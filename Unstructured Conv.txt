## 4. The End-to-End Pipeline (Conceptually)

1. **Entry** — patient reaches the system through any of the 3 access points; identity + consent captured
2. **Conversational capture** — speech goes to ASR (Bhashini/IndicWhisper) in short turns → transcript → an LLM dialogue manager constrained to a clinical ontology (SOCRATES for allopathic, Dashavidha Pariksha for AYUSH) decides the next question or marks the section complete
3. **Document capture (parallel)** — camera images → cleanup (deskew, contrast) → OCR → an extraction LLM pulls diagnoses, drugs, dosages, lab values into structured fields, ordered by date
4. **Continuous safety check** — a red-flag classifier watches the conversation live; once medications are known (from either voice or OCR), the herb-drug interaction check runs against the combined list
5. **Synthesis** — a summarization step merges the conversational history and the digitized documents into one physician-format note
6. **Eligibility check** — a separate rules engine runs against the demographic fields already captured, independent of the medical pipeline
7. **Consent-gated push** — the structured note and document timeline are sent to the hospital's system and, in the sandbox/certified flow, linked to ABHA
8. **Routing** — a token and department are assigned based on the chief complaint/triage outcome
9. **Consult** — the doctor sees the structured draft the moment the patient walks in, edits or confirms it, and that becomes the actual medical record
10. **Teardown** — temporary local session data is wiped once submission completes, per the consent design

## ML + Offline: Is Dual Architecture Doable?

Short answer: **yes, but not uniformly** — and the honest breakdown matters more than a blanket "yes":

**Doesn't need ML at all, works offline trivially:**
- The AYUSH touch/icon-based Dashavidha Pariksha module — it's just structured UI logic (tap the picture that matches), no model required either way
- The scheme-eligibility checker — should be a deterministic rules engine, not an LLM call, regardless of connectivity (more auditable, and judges will trust a rules engine over "the AI decided you're eligible")
- Basic red-flag safety net — the emergency-symptom trigger is exactly the kind of thing that should **not** depend on a model or connectivity. A lightweight keyword/rule-based layer that always runs locally, with the LLM as an *additional* layer only when online, is the safer design here — a safety-critical check shouldn't have a single point of failure that's "no internet."

**Needs ML, degrades gracefully offline:**
- OCR — Tesseract/PaddleOCR run fully on-device already, no cloud dependency; only the LLM-based *entity extraction* on top (turning raw OCR text into structured drug names/dosages) needs a model, and a small quantized one can run locally at reduced accuracy
- Voice ASR — a distilled/quantized local model (Whisper-tiny/base class, or a compressed IndicWhisper) can run offline, but accuracy will be visibly worse than the full cloud-hosted model. That's a real tradeoff, not a free win

**Genuinely hard to fully replicate offline:**
- The adaptive dialogue manager (deciding the *next best question* based on everything said so far) — a small local LLM can approximate this, but quality drops noticeably against a large cloud model. This is where "dual architecture" earns its name: a lightweight local model for offline sessions, swapped for the full model when connectivity returns.

**On implementation** — you've actually already solved this exact problem once. Sahakar's `model_router.rs` / `brain_switcher.rs` is precisely a "route between local and larger models based on availability/constraints" pattern. That's directly reusable thinking here: MediKiosk's offline/online switch is the same architectural shape — router checks connectivity, picks the local quantized model or the cloud one, everything downstream (dialogue manager, extraction, summarizer) doesn't need to know which one answered.

**Practical scope for a 36-hour build:** don't try to make everything work offline. Pick the "store-and-forward" pattern as your baseline (capture audio/images/answers locally via IndexedDB, sync when signal returns) and layer the local-model fallback on top only for the adaptive-questioning piece as your stretch/demo-differentiator — that's a strong, honest "we thought about rural connectivity" story without overclaiming full offline parity.

## Government Scheme Feature — How to Actually Build It

Skip the RAG/vector-store approach from the doc for this specific feature — eligibility is a binary/rules question, not a "retrieve similar text" question, and an LLM inferring eligibility from embedded PDF chunks can hallucinate a wrong yes/no on something with real financial consequences for the patient.

1. **Get the actual published criteria, not memory or an API.** There's no live eligibility API for PM-JAY, Aarogyasri, CGHS, or RAN — pull the official guideline PDFs from the National Health Authority (PM-JAY) and each relevant state/central health department, and hand-encode the real criteria as a small config file per scheme (JSON/YAML: which fields matter, what values qualify).
   - One correction worth knowing before you encode this: PM-JAY eligibility isn't primarily income-based — it's driven by **SECC 2011 deprivation/occupational categories** (i.e., whether the household is listed in that census by specific deprivation criteria), not a self-declared income threshold. A rule like "income < ₹X" would be factually wrong. The safer question to ask the patient is "do you have a ration card of type X" or "are you already listed/enrolled," and point them to the official portal for the real check rather than computing it yourself.
2. **A plain deterministic function evaluates the rules.** No LLM involved in the yes/no decision — just conditionals against the fields you collected.
3. **The LLM's only job here is translation/phrasing** — turning "matched: PM-JAY, ration-card-based" into a friendly sentence in the patient's language, and formatting the document checklist. It never decides eligibility.
4. **Every output ends with "confirm at the official portal / hospital welfare desk."** You're a pre-screener that removes "I didn't know I might qualify," not a legal determination.

## Noise Handling — The Actual Priority Order

You don't need custom neural denoising as your first move — most of this problem is solved by settings you already have access to.

1. **Start here, costs nothing:** when you call `getUserMedia()` in the browser, just set `echoCancellation: true, noiseSuppression: true, autoGainControl: true`. This is a one-line config, not custom DSP — modern browsers already run decent adaptive noise suppression under the hood. Do this before building anything else.
2. **If that's not enough, add a light server-side pass**, not a heavy one: Python's `noisereduce` library (spectral gating) is a few lines to wire in after upload, before ASR. Far simpler to integrate under time pressure than compiling RNNoise/DeepFilterNet to WebAssembly.
3. **Full neural denoising (RNNoise/DeepFilterNet WASM) is a stretch goal**, not a baseline — put it on day 4-5 if time allows, and don't let it block your core pipeline.
4. **Don't ignore the physical layer.** A short on-screen prompt ("please hold the mic side close to your mouth") does real work for free. If budget allows even slightly, a ₹200-500 clip-on lapel mic for the hospital tablets is a peripheral accessory, not custom hardware — still fits the software track, and meaningfully improves capture quality in a loud OPD.
5. **Always show the live transcript** so the patient/volunteer can catch an obvious mishearing immediately and retype — a fast human-correction loop beats chasing perfect audio.

## The Floating Autonomous Assistant — Yes, Genuinely Buildable, With One Honest Caveat

What you're describing is a **function-calling agent**, and it's very achievable with what you're already building — it's not a separate "computer use" system, it's the same LLM you use for dialogue, given a different job.

**How it actually works:**
1. Define a fixed, whitelisted set of app-level actions as a tool schema: `navigate_to(screen)`, `fill_field(field_id, value)`, `start_document_scan()`, `open_scheme_checker()`, `read_summary_aloud()`, `submit_history()`, etc.
2. The floating mic (small, corner, always present) listens on tap or a wake phrase.
3. Speech → ASR → transcript. That transcript, plus the current screen state and the list of available actions, goes to the LLM.
4. The LLM returns **one structured action call** — not free-form text, not arbitrary DOM manipulation — and the frontend executes it directly (router navigation, form fill, whatever the action is).
5. A brief spoken/visual confirmation follows ("Opening document scan now").

**Where "fully autonomous" should mean exactly that, and where it shouldn't:**
- Navigation, reading things aloud, opening a screen, showing the checklist — execute immediately, zero friction, genuinely seamless. No reason to slow this down.
- Anything that **writes clinical data or submits to HIS/ABDM** — insert one lightweight confirm step ("You said chest pain since this morning — is that right?") before it commits. This isn't a technical limitation; it's a deliberate boundary given that ASR can mishear a symptom, and a misfired autonomous write into a medical record is a real failure mode, not a hypothetical one. When a judge asks "what happens if it mishears you," you want an answer better than "it just writes it in."

That split — instant for navigation, one-tap-confirm for anything that changes the medical record — is what makes this "fully intelligent and seamless" *and* defensible in a healthcare context, rather than a flashy demo with an obvious hole in it. Practically: this reuses your existing dialogue-management LLM call with a different system prompt and a small function-calling schema, so it's not a new subsystem — it's the same brain doing a second job.

## "Every Scheme Based on City" — One Correction First

Health schemes in India are granted at the **state** level, not city level — a scheme like Aarogyasri doesn't change whether the patient is in Hyderabad or a small Telangana town; it's the state that administers it, not the municipality. So "city" isn't quite the right filter — you want **state**, and city is really just a way of inferring the state (or you skip the inference and just ask state directly, which is more reliable than reverse-geocoding a city name).

And it's genuinely more varied than "one scheme per state" — I checked current examples, and the eligibility logic differs meaningfully:

| State | Scheme | How eligibility works |
|---|---|---|
| Rajasthan | Chiranjeevi (₹25L) | Universal — covers **all** families, small annual registration fee |
| West Bengal | Swasthya Sathi (₹5L) | Universal — all state residents |
| Andhra Pradesh | YSR Aarogyasri (₹25L) | Income/BPL-based |
| Maharashtra | MJPJAY | Ration-card category based, **now integrated with PM-JAY** — one claim can satisfy both |
| Tamil Nadu | CMCHIS / Kalaignar | Income-threshold based, separate empanelment from PM-JAY |
| Karnataka | Arogya Bhagya | State top-up alongside PM-JAY |

This matters practically: a rules engine that assumes "check income against a threshold" for every state will be wrong for Rajasthan and West Bengal (universal, no income test) and wrong in a different way for Maharashtra (ration-card category, not income). **Your rule schema needs a `type` field per scheme** — `universal`, `income_threshold`, `ration_card_category`, `secc_deprivation` — not one shared logic path.

## How to Actually Scale This to "Every Scheme"

Realistically build it as **data, not code**, so "every state" is a data-entry problem you can grow after the hackathon, not a rewrite:

1. One record per scheme: `{state, scheme_name, type, criteria: {...}, coverage_amount, integrates_with_pmjay: bool}` — a flat table/JSON, not per-scheme hardcoded functions.
2. One evaluator function that reads `type` and applies the right check — universal → auto-match on state alone; income-based → compare declared bracket; ration-card-based → compare card category; SECC-based → "are you already listed" question, don't compute it yourself (mentioned last time — still true for PM-JAY itself).
3. For the hackathon, seed maybe 6-8 real schemes covering a spread of types (PM-JAY + CGHS/RAN nationally, plus 3-4 states like the ones above, chosen so your demo shows at least one universal, one income-based, and one PM-JAY-integrated scheme — that variety is what proves the engine actually generalizes, not just hardcoded for one case).
4. Pitch line that's both honest and strong: *"the schema supports all 28 states/UTs — we've seeded N as working proof; scaling to the rest is data entry, not new engineering."* Judges respond well to "architecturally complete, data-incomplete by design" — it's a true and confident claim, unlike promising full national coverage you haven't built.

## The Green/Red/Back Pattern — This Is a Good Design, Here's How to Make It Work Well

You've actually landed on a clean solution to the exact "what if the AI mishears" problem from before. A few refinements to make it functional rather than just three colored buttons:

- **Always pair the buttons with a readback**, spoken and shown as text — "You said: Hyderabad" — *then* green/red/back. Buttons alone, with nothing displayed to confirm, don't catch anything; the readback is what actually lets the patient catch a mishearing.
- **Icon + color together, not color alone** — a checkmark and an X, not just green and red — for the same low-literacy, possibly colorblind-inclusive reasons as everywhere else in this app.
- **Scope it to assistant-driven writes, not everything.** Reserve this 3-button confirm loop for moments where the assistant filled something on the patient's behalf (a symptom, a state selection, a scheme detail) — not for pure navigation ("opening document scan"), which can stay instant with just a brief toast/audio cue. If every single autonomous action needs a button press, "extraordinarily autonomous" turns into "extraordinarily many taps," which undercuts the exact seamlessness you're going for. Manual chip-taps also skip this loop — the confirm step exists specifically because the *AI* interpreted something, not because a human tapped an option themselves.
- **Retry vs. Back, defined precisely:** Red/Retry re-listens for the *same* question and re-attempts the fill — it doesn't move the flow anywhere. Back steps to the *previous* screen/question and should leave that earlier answer editable rather than wiped — discarding an answer someone already gave reintroduces the "repeat yourself" problem you're trying to eliminate everywhere else in this project.

This pattern, applied consistently, is what actually earns you the "universal" claim — one interaction rule (assistant acts → readback → confirm/retry/back) that works identically whether it's filling "which state are you in" on screen one or "what's your chief complaint" on screen five. That consistency is more convincing to judges than raw autonomy would be on its own.

## NLP / "Understand It Even When Phrased Differently" — How This Actually Gets Built

Good news first: using an LLM (which you already are, for the dialogue manager) already gets you most of this for free — LLMs generalize over paraphrase and indirect phrasing by nature, because they're not doing keyword matching. The real engineering risk isn't "it can't understand similar phrasing" — it's the opposite: an LLM will confidently generalize even when it *shouldn't*, silently mapping something ambiguous to the wrong thing. So the actual work is calibrating confidence and verifying uncertain matches, not teaching it to understand paraphrase.

Concretely, four pieces make this real rather than aspirational:

1. **A semantic-similarity layer for routing, not string matching.** When a patient's utterance needs to map to a known intent/chip/symptom category, compare it via embeddings (Sarvam or NIM both expose embedding models) against your canonical set — this is what actually catches "similar but not identical" phrasing reliably, rather than hoping the LLM's raw output happens to line up.

2. **Extend the Babel Fish layer into a real controlled-vocabulary mapping**, not just idiom translation. Right now it converts phrases like "chhati pe patthar" into medical English — extend that same mechanism into a broader dialect/synonym-to-standard-term dictionary. This isn't just UX polish: FHIR/ABDM ultimately wants coded terms (SNOMED-CT style), not free text, so this normalization step is functionally required regardless — you're not adding new scope, you're making an existing requirement actually work.

3. **Confidence-gated confirmation, reusing what you already built.** When the semantic match confidence is low — genuinely ambiguous phrasing, a dialect the model handles poorly — trigger the same Green/Red/Back readback loop you already have, just on a new trigger condition (low confidence) instead of only "AI acted autonomously." No new UI component needed, just a second reason to fire the one you have.

4. **Full conversation context, always, with an explicit cross-reference instruction.** The "human-like thinking" quality — connecting a diabetes mention in question 3 to a numbness complaint in question 9 — comes from passing the *entire* conversation to each interpretation step (not treating each answer in isolation) and explicitly prompting the model to check new answers against everything said earlier. Then your existing summary generator (Module C) gets one more instruction: surface a short "connections for the doctor's attention" section — e.g., "patient reports foot numbness; earlier reported diabetic history — consider peripheral neuropathy screening" — clearly separated from the raw transcript, framed as a flag, never a diagnosis. This is a prompting change to something you've already built, not a new subsystem.
